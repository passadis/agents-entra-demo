A field guide to agent identity

01 / FOUNDATION

Microsoft Entra ID

The identity provider authenticates people and workloads, issues tokens, and supports access policies. An identity proves who is calling; the resource still decides what that caller can do.

02 / AGENT CLASS

Agent identity blueprint

An application object defines a class of agents and holds its credentials. Its blueprint principal represents it within a tenant. Credential sharing makes the blueprint an important trust boundary.

03 / INDIVIDUAL ACTOR

Agent identity

A specialized service principal represents an agent instance. Direct permissions can differ between agents. A sponsor is accountable for its purpose and lifecycle. Agents do not store their own credentials.

04 / AUTHENTICATION

Two-step token exchange

Azure managed identity authenticates the blueprint. A token request with fmi_path identifies the child agent. The blueprint exchange token is then used to obtain the agent's resource token.

05 / AUTHORIZATION

Declarations ≠ grants

Required resource access declares permissions for consent review. Inheritance configuration plus administrator consent enables inherited permissions. A permission declaration alone grants no access. This demo provisions direct application roles.

06 / APPLICATION POLICY

Governance beyond tokens

Spending ceilings, depot boundaries, approvals, and review deadlines are enforced by this application. They are not native blueprint schema fields or a substitute for tenant Conditional Access.

What this demonstration proves

The default planner is deterministic; an optional Azure OpenAI planner proposes real function calls. Purchase orders and supplier data are fictional in both modes. The fixture supplier-note scenario deliberately proposes an ungranted tool; it is not a general prompt-injection detector. Local controls do not modify your Entra tenant. The supplied provisioning scripts create live identity resources separately.
